1. Overview

Roaster is an AI-powered code review tool: paste code into a Monaco editor, submit it, and a local Ollama LLM returns sarcastic-but-accurate inline line comments. Reply to any comment and the AI argues back in a threaded conversation.

Key Decisions

  • 1 session : 1 live submission. Resubmitting replaces the payload and drops the old review.
  • Per-file AI review, not one giant prompt. Each file gets its own Ollama call and context budget.
  • Defensive JSON parsing, never throws. Degrades through fallback stages instead of failing the whole review.
  • Soft delete for sessions. IsActive flag — audit Event rows always stay valid.
  • CorrelationId = SessionId. Stable identifier for grouping a session's full history.

Submission Flow

POST /api/submissions
  -> Validate (sessionId, code 1-50k chars, language enum), strip control chars
  -> No existing submission  -> create (Status=Submitted)
  -> Existing + Processing   -> 409 Conflict
  -> Existing + other status -> replace Payload, reset Status=Submitted, drop old Review
  -> Log Event(Submitted), publish SubmissionCreatedEvent -> 202 Accepted

RabbitMQ "code-submitted" (PrefetchCount=1, ConcurrentMessageLimit=1)
  -> CodeSubmittedConsumer: Status -> Processing -> Event(ProcessingStarted)
  -> IAiReviewService.ReviewCodeAsync()
  -> Success: save Review + ReviewMetrics + Event(ReviewCompleted), Status -> Completed
  -> Parse failure: Status -> Failed, Event(Failed) with real parser error in Metadata
  -> Exception: Status -> Failed, Event(Failed) with ex.Message, rethrow -> MassTransit retry

Key Patterns

  • Service layer. One service per resource; services return ServiceResult<T> (implements IResult).
  • JSONB owned types. Submission.Payloads, Review.Comments, Event.Metadata.
  • MassTransit retry. CodeSubmittedConsumer: exponential (3x, 10s-120s). UserThreadReplyConsumer: fixed [3s, 10s, 30s].
  • AI JSON parsing never throws. 4 fallback stages before giving up; the real parser error (or context-length-exceeded hint) lands in the Failed event's Metadata.

5. AI Pipeline

Roaster.Reviewer — AiReviewService — talks to a local Ollama model through Semantic Kernel's IChatCompletionService. Code is reviewed one file at a time, using one of two fixed system prompts. No agent framework, planner, tool use, or memory store — two prompt personas sharing one call mechanism.

Initial Review — Per-File Loop

flowchart TD A["files: list of CodeFileInput"] --> B["For each file"] B --> C["Render file-message template (fileName, language, numbered lines)"] C --> D["ChatHistory = roaster.txt + file message"] D --> E["Ollama call (num_ctx = ContextLength)"] E --> F["ReviewResponseParser.Parse"] F -->|parsed| G["Pool comments + summary"] F -->|failed| H["Record per-file error, skip"] G --> I{"More files?"} H --> I I -->|yes| B I -->|no| J{"Any file parsed OK?"} J -->|yes| K["Status = Success"] J -->|no| L["Status = Failed, Error = joined per-file reasons"]

Each file is judged in isolation — bounds the context-overflow risk to a single file's size instead of the whole submission's, at the cost of cross-file reasoning.

Line numbering. Content is split into lines, each prefixed with its 1-indexed number before being sent — this is the entire reason the model returns accurate line numbers; it echoes numbers it was shown, not values it computes.

roaster.txt persona. Senior engineer, sarcastic. Must return only JSON: summary + comments[] (fileName, lineNumber, comment, severity). Severity: 10 = should-fix, 20 = must-fix.

Context Length (num_ctx)

Every call passes num_ctx = ContextLength. Default 8096 (OLLAMA_CONTEXT_LENGTH in Docker Compose, appsettings.json for local dev). This budget is shared by the prompt (system prompt + one file's numbered content) and the response. qwen2.5-coder models natively support up to 32,768 tokens — the ceiling here is a deliberate memory/quality tradeoff, not a model limit.

If a file's content pushes the prompt at/over ContextLength, Ollama truncates silently. AiReviewService detects this and prefixes the per-file error with a context-exceeded hint, so a truncation failure reads differently from a genuine malformed-JSON failure in the Events UI.

Defensive JSON Parsing

ReviewResponseParser.Parse — 4-stage fallback, never throws:

  1. Direct JsonSerializer.Deserialize.
  2. Strip a markdown JSON fence via regex, retry.
  3. Substring from first { to last }, retry.
  4. Escape raw newlines/tabs found inside string literals, retry.

On total failure: the real JsonException message + a raw-response snippet becomes ReviewerResult.Error, which flows into the Event(Failed) row's Metadata — visible in the UI, not a generic placeholder.

Thread Replies — Second Persona

code            = ALL files in the submission, joined together
originalComment = the review comment that started this thread
priorHistory    = every prior ThreadReply, oldest first
userMessage     = the newest reply

ChatHistory(replier.txt)
  + "Code: {code} / Original comment: {originalComment}"
  + assistant(originalComment)
  + priorHistory (user/assistant alternating)
  + user(userMessage)
-> Ollama -> plain-text reply (no JSON, no parsing)

Known limitation: code is every file in the submission concatenated, not just the file the comment is in — a multi-file submission resends its full code on every reply.

"How many agents?"

Two system-prompt configurations, not two autonomous agents. Neither calls tools/functions, runs a planning loop, or maintains memory beyond the explicit chat history passed in. All decision logic lives in application code.

Tool-Calling — Tried and Shelved

Real function-calling was tested against qwen2.5-coder:3b and deepseek-coder:1.3b: both raw Ollama tools arrays and Semantic Kernel's FunctionChoiceBehavior.Auto() produced function-call-shaped text, never an actual invocation. Not usable with these models — cross-file retrieval was shelved rather than half-built.

6. Data Model

erDiagram SESSION ||--o| SUBMISSION : "1 to 1" SUBMISSION ||--o| REVIEW : "1 to 1" REVIEW ||--o{ COMMENTTHREAD : "1 to N" COMMENTTHREAD ||--o{ THREADREPLY : "1 to N" SUBMISSION ||--o{ EVENT : "1 to N" REVIEW ||--o| REVIEWMETRICS : "1 to 1" SESSION { uuid Id PK varchar Name timestamp CreatedAt bool IsActive } SUBMISSION { bigint Id PK uuid SessionId FK jsonb Payloads smallint Status } REVIEW { bigint Id PK bigint SubmissionId FK text Summary jsonb Comments } COMMENTTHREAD { bigint Id PK bigint ReviewId FK int LineNumber smallint Status } THREADREPLY { bigint Id PK bigint ThreadId FK text Content bool IsAiReply } EVENT { bigint Id PK bigint SubmissionId FK uuid SessionId smallint EventType uuid CorrelationId jsonb Metadata } REVIEWMETRICS { bigint Id PK bigint ReviewId FK varchar ModelId int QueueWaitMs int ReviewDurationMs }

Enum Values (all smallint)

EnumValues
SubmissionStatus10=Submitted, 20=Processing, 30=Completed, 40=Failed
ThreadStatus10=Unresolved (default), 20=Resolved
ReviewSeverity10=Gentle, 20=Medium, 30=Brutal
EventType10=Submitted, 20=ProcessingStarted, 30=ReviewCompleted, 40=Failed, 50=UserReplied, 60=AiReplied

JSONB Owned Types

  • Submission.Payloads → list of {FileName, Content, Language} — one entry per file.
  • Review.Comments → list of {FileName, LineNumber, Comment, Severity}.
  • Event.Metadata → arbitrary JSON — token usage on success, real parser/exception error on failure. Rendered via JsonViewer.razor.
