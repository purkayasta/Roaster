1. One-line pitch

You paste code into a Blazor editor, submit it, and a background worker sends it to a local LLM (Ollama, qwen2.5-coder:3b) through Semantic Kernel, which returns a JSON review (summary + per-line comments, sarcastic tone). You can reply to any comment and the AI argues back, keeping full chat history per thread. Everything is async: submit returns 202, the frontend polls for the result.

4. Multi-file review — how it actually works

Likely question "How does the AI understand relationships between files?"

Honest answer: it doesn't have any structural understanding — no AST, no import graph, no symbol resolution. All files are concatenated into one prompt as plain text, and whatever cross-file reasoning happens is purely the LLM reading everything in the same context window and inferring relationships from surface text (matching type/function names, file headers). There is no dependency graph built by the app.

The actual mechanism — AiReviewService.ReviewCodeAsync (updated: one chunk per file)

foreach (file in files):
    history = new ChatHistory(roaster.txt system prompt)
    history.AddUserMessage( render(file-message.txt template, {fileName, language, numberedContent}) )
    response = chat.GetChatMessageContentsAsync(history, executionSettings)   ── separate call, per file
    parse response → comments + summary; skip file on parse failure, keep going
merge: all comments pooled into one list; summaries joined as "fileName: summary" per file
overall status = Success if ANY file parsed OK, Failed only if EVERY file failed to parse

Changed This used to be one prompt containing every file concatenated together. It's now one Ollama call per file — each file gets its own bounded prompt (system prompt + that file's line-numbered content only), so total submission size no longer determines whether a single call blows the context window. A large multi-file submission is now N small calls instead of 1 huge one.

Trade-off this creates: the model reviewing Bar.cs never sees Foo.cs in the same call anymore — cross-file reasoning that used to be theoretically possible (if everything fit) is now structurally impossible, because each file is reviewed in total isolation. The old approach failed at scale but could at least see everything; this one scales but can't relate files at all. That gap is exactly why tool-based cross-file retrieval (§11) was explored next — and why it matters that the finding there was negative.

Multi-file is still fundamentally a UI/data-model feature too (the "Multi file" toggle in NewSessionDialog → Submission.Payloads is a List<Payload>), but the review engine now treats each payload as an independent unit of work rather than one shared context.

5. Prompting strategy

Prompt fileRoleKey contract
roaster.txtSystem prompt for the initial reviewForces strict JSON only: { summary, comments: [{ fileName, lineNumber, comment, severity }] }. Severity is a fixed enum (10=should fix, 20=must fix). Persona: senior engineer + sarcastic jab, correctness first, joke second.
replier.txtSystem prompt for thread repliesPlain text, no JSON, savage/argumentative tone, told explicitly not to repeat the original comment.
file-message.txtNew per-file user message templateRendered via SK's KernelPromptTemplateFactory/IPromptTemplate with {{$fileName}}, {{$language}}, {{$numberedContent}} — replaces a hand-rolled StringBuilder. Line-numbering itself stays procedural (a template can't do that part); the template only owns the declarative "=== File: X (lang) ===" shape.

Prompts are embedded resources (compiled into the DLL, not read from disk at runtime) loaded once via PromptLoader static readonly fields — cheap, no file I/O per request, but means changing tone requires a rebuild/redeploy, not a config change.

Execution settings, not just prompt text: every chat call now passes an OllamaPromptExecutionSettings with ExtensionData["num_ctx"] = contextLength — verified (via a throwaway HTTP-listener harness) that this actually lands in the outgoing Ollama request body under options.num_ctx. Context length comes from config (Ollama:ContextLength), not a hardcoded default, because different models need different values — a 3B model and a 7B model don't share a sane context budget.

Why JSON-only matters here

Local 3B-class models are not natively function-calling / structured-output models the way hosted GPT-4o-style APIs are — there's no response_format=json_schema guarantee. The app leans entirely on prompt instruction ("Return ONLY a valid JSON object") plus a defensive parser as the real safety net:

ReviewResponseParser.Parse(raw): 1. direct JsonSerializer.Deserialize 2. strip ```json fences via regex, retry 3. substring from first '{' to last '}', retry 4. give up → ReviewStatus.Failed, empty result (never throws)

This is the single most important resilience mechanism in the AI path — a small local model will occasionally wrap JSON in prose or markdown, and this is what keeps that from being a hard failure.

6. Local LLM limits — the hard interview questions

Q: How much code can Ollama take before failing / what's the max?

Fixed This used to be a real gap: num_ctx was never set, so the connector silently ran on whatever context window Ollama/the model defaulted to. Now OllamaOptions.ContextLength is a required config value (Ollama:ContextLength in appsettings.json, Ollama__ContextLength env var in docker-compose, no hardcoded default in code) and is applied on every call via OllamaPromptExecutionSettings { ExtensionData = { ["num_ctx"] = contextLength } }. Verified this actually reaches Ollama by intercepting the raw HTTP request body — options.num_ctx is present and correct. It's required-not-optional deliberately: different models need different context budgets (a 3B model and a 7B model don't share a sane default), so the value must be supplied per deployment, not assumed.

What's still not covered: no proactive token counting before sending — if a single file's content itself exceeds the configured num_ctx, Ollama still truncates silently with no warning surfaced to the user. Per-file chunking (below) shrinks the blast radius to one file instead of an entire multi-file submission, but doesn't eliminate the risk for one very large file.

The API-layer guardrail is unchanged: SubmissionRequest validation still caps code at 50,000 characters per submission (Roaster.Api) — a size sanity check, not a real token budget.

Q: What happens with 10 files / very large multi-file submissions?

Changed This used to be the scary case: all 10 files concatenated into one prompt, one context window shared across everything. Now each file gets its own call — ReviewCodeAsync loops over files, one bounded prompt per file, and merges the per-file JSON results afterward (pooled comments, joined summaries). 10 files means 10 sequential Ollama calls, not one giant one — total submission size no longer determines whether a single call overflows context. The trade-off: since each file is now reviewed in isolation, the model can never relate file A to file B even if both would've fit in one window before — see §11 for why cross-file retrieval (the fix for that) was tried and shelved.

Q: Why a 3B model? Why local at all?

Cost/privacy (code never leaves the machine) and simplicity of the demo (no API key, no billing). Trade-off is explicit: a 3B coder model is noticeably weaker than hosted frontier models at holding multi-file context and producing consistently well-formed JSON — which is exactly why the defensive parser (§5) exists instead of trusting the model's output format.

8. Reliability & retries

  • Serial processing: PrefetchCount=1, ConcurrentMessageLimit=1 on code-submitted — only one review runs at a time. Deliberate: a local Ollama instance has one GPU/CPU to share; concurrency would just queue inside Ollama anyway.
  • Retry: exponential (3 attempts, 10s→120s) for reviews; fixed intervals [3s,10s,30s] for thread replies. Consumer explicitly rethrows on AI failure so MassTransit's retry actually fires — swallowing the exception would silently strand the submission in Processing.
  • Idempotency guard: consumer discards a SubmissionCreatedEvent if the submission's current status isn't Submitted anymore (stale/duplicate message after a resubmit).
  • Parser never throws: a malformed AI response degrades to ReviewStatus.Failed with an empty comment list rather than an unhandled exception — but the consumer still marks the submission Failed and lets MassTransit retry the whole review, since a retry might get a well-formed response from the same model.

No test ever hits a real Ollama instance — the AI is always mocked/stubbed. That's correct for CI speed and determinism, but means prompt quality and real-model JSON compliance are untested by the suite — worth naming as a known gap, not hiding it, if asked "how do you know the prompt works."

10. Deliberate trade-offs / what's missing

  • No SignalR/real-time push — frontend polls GET .../review. Simpler, no persistent connection to manage, costs a poll interval of latency.
  • No cross-file reasoning — per-file chunking (§4, §6) fixed the context-overflow risk but means each file is reviewed in total isolation now; a bug that spans two files can't be caught. Tried to fix this with tool-calling-based retrieval, shelved after live testing (§11).
  • No proactive token counting — num_ctx is now explicitly configured (fixed, §6), but nothing counts tokens before sending or warns if one file's content alone would overflow it.
  • Schema via DbUp, not EF Migrations — full control over SQL, no migration-history table lock-in, but two systems (EF models + hand-written SQL) must be kept in sync manually.
  • AI as in-process library — no independent scaling of review throughput separate from the Consumer process.

11. Semantic Kernel reality check — tool-calling tested live

The obvious next step for fixing "no cross-file reasoning" (§10) was giving the model a tool to fetch other files on demand — a Kernel function like GetFileContent(fileName) with FunctionChoiceBehavior.Auto(). Before building it, this was tested directly against the actual local models rather than assumed to work — it doesn't, and the reason why is worth knowing cold.

Conclusion & decision

Real function/tool-calling is not usable with the models this project runs, full stop — confirmed with two independent tests, not inferred from documentation or the "tools" capability tag (which turned out to be misleading for this model). That closes off both:

  • Cross-file retrieval via tool calls (the fix for §10's isolation problem) — the model can't reliably call a GetFileContent function even if one is registered.
  • Tool-forced structured output — can't force a schema-shaped function call as the response format either, for the same underlying reason.

There is a real, working path to reliable structured JSON — Ollama's constrained format field — but it requires bypassing the SK Ollama connector for that specific call (raw HTTP or OllamaSharp directly), since the connector can't pass it through even in the newest alpha build. Given that trade-off, both were shelved for now rather than half-implemented on a foundation that doesn't hold. What shipped instead: per-file chunking (§4/§6) and configurable num_ctx (§6) — both of which work with the current models today — plus SK prompt templates (§5) for the parts of the system that don't depend on tool-calling at all.

Why this is worth telling an interviewer: it's a concrete example of testing a claim ("the model supports tools") against reality instead of trusting a capability tag, and making a scoped call not to build on a foundation proven not to work — rather than shipping something that looks done but silently doesn't function.

12. Rapid-fire Q&A prep

Q: Why RabbitMQ instead of calling the AI synchronously from the API?

Local LLM inference is slow (seconds) and this is a background job, not a request/response operation — sync would block HTTP threads and force clients to hold a connection open. Async + poll decouples submission speed from review latency and gives free retry semantics via MassTransit.

Q: What's the single most fragile part of this system?

The AI response contract — a 3B local model returning valid JSON on every call isn't guaranteed. The defensive 3-stage parser is the mitigation, but it's a workaround for a fundamentally unreliable structured-output guarantee, not a fix.

Q: How would you scale this to more concurrent reviews?

Raise ConcurrentMessageLimit only if backed by more Ollama capacity (multiple model instances/GPUs) — right now it's intentionally 1 because there's exactly one local model to share. Horizontal scale would mean running multiple Ollama backends and load-balancing the Consumer's calls, not just raising the MassTransit limit.

Q: Does the model support function/tool calling?

No — tested directly, twice (raw Ollama API and full SK Kernel with FunctionChoiceBehavior.Auto()), against qwen2.5-coder:3b. Both times the model printed function-call-shaped JSON as plain text instead of populating Ollama's tool_calls field. Ollama's own capability tag says "tools" for this model, which is misleading in practice — always verify against the actual model+runtime combination rather than trusting the tag. See §11.

Q: What does Semantic Kernel actually give you in this project?

Two real things, both proven by testing rather than assumed: a swappable chat-completion abstraction (Ollama ↔ Azure OpenAI is a one-line change), and prompt templating (KernelPromptTemplateFactory for the per-file message, §5). It does not give this project function calling or structured output — both were tested and don't work with the current models/connector, so nothing in the shipped code depends on them.
